Personio Assistant: Architecture Redesign

An overview of work I lead to drive the strategy, design, and architecture of the Personio Assistant.

Role
Principal Product Designer
Timeline
December 2024 - January 2026
Team
PM, Front-end Engineer, 7 Backend/ML Engineers
Build Time
2 afternoons (Dec 16-17, 2024)

The Problem

After months of tactical UX improvements to Personio's AI Assistant, the fundamental issues remained:

Technical Failures:

  • CSAT still at 19%
  • Wrong answers, incorrect dates, irrelevant content
  • No page context awareness
  • Slow, unreliable tool calling
  • Complex, poorly documented architecture using Claude through Bedrock + ML models + Knowledge bases

Organizational Pressure:

  • CEO and COO openly complaining about reliability in Slack
  • Team had been spared during massive layoffs (80% of US workforce eliminated) specifically because "AI is a priority"
  • Dramatic staff reduction meant fewer resources to tackle harder problems
  • AI positioned as competitive differentiator, but failing to deliver

Personal Frustration:

  • I couldn't grasp the structure of our existing system
  • No definitive design document showing how everything worked
  • Tried to replace the existing AI backend in production — failed due to infrastructure complexity

The Core Realization:

The incremental UX fixes I'd shipped were improving symptoms, not causes. The assistant's architecture was fundamentally flawed. We needed a different approach entirely.

The Decision to Rebuild

Rather than continue fighting the existing system's complexity, I decided to build a new assistant from scratch. But I needed to do it in a way that:

  1. Didn't require the full team: Resources were limited after layoffs
  2. Didn't disrupt production: The existing assistant had to keep running
  3. Could demonstrate value quickly: Leadership needed proof of concept, not promises
  4. Used modern AI techniques: Claude's Agent SDK, latest models, better context handling

The Chrome Extension Strategy:

Instead of building within the Personio app, I would build a Chrome extension. This gave me:

  • Sidepanel API: A persistent panel that doesn't obstruct the page
  • Native Chrome capabilities: Access to activeTab and browser manipulation
  • Rapid prototyping: No need to navigate internal UI complexity
  • Distribution flexibility: Could be "AI Labs" beta product for customers and internal teams

If successful, this would become a sandbox for other teams to prototype AI interactions without the AI team as a bottleneck.

What I Built

Architecture

Chrome Extension Structure:

  • Sidepanel: Persistent chat interface using Chrome's Sidepanel API
  • Service Worker: Manages background processes and communication
  • Injected Scripts: Read and manipulate page content
  • Navigation Map: Custom-built structure to help the agent understand Personio's information architecture

Context System:

The key architectural difference from our production assistant: page context awareness.

What gets captured (text-based, up to 5,000 characters):

  • Page title
  • Meta description
  • Headings (H1, H2, H3)
  • Main content
  • Selected text
  • Modal content

When context is captured:

  • Initial fetch when sidepanel opens
  • On tab switch
  • On page load / URL change
  • Before each message sent (refreshes to get latest selected text)

How context is sent to Claude:

  • Included with every query
  • Embedded in system prompt as <page_context> block (not user message)
  • Agent can refresh context via read_page_content tool after taking actions

Capabilities

1. Page Context Awareness

The production assistant couldn't see what was on the page. This meant users would ask questions about content visible right in front of them, and the assistant would fail.

My prototype can answer questions about the current page because it has access to structured text content.

2. UI Navigation

The assistant can navigate Personio's interface using the navigation map I built. When a user asks to go somewhere, the agent can find and click the appropriate navigation elements.

Example:

  • User: "Show me my payslips"
  • Agent: Navigates to correct page

3. Action Execution (Semi-Agentic)

The most impressive capability: the assistant can execute workflows on behalf of users.

"Request Time Off" workflow:

  1. User: "I need to request time off next Monday"
  2. Agent recognizes intent
  3. Navigates to "Team and Calendar" page
  4. Clicks "Request time off" button
  5. Modal opens
  6. Selects type of time off
  7. Selects the dates
  8. [Currently stops here — doesn't submit yet]

[VIDEO: Full "Request time off" workflow demo]

4. Context Drawer (Dynamic Prompts)

Inspired by Perplexity's Comet Browser, I designed a context drawer that sits above the input field.

What it shows:

  • Title of current page
  • When expanded: List of prompts available from current view
  • Updates as user navigates the app

The Vision (Federated AI Model):

This drawer becomes the "control pad" for any surface in Personio. Product teams can:

  • Define what the AI can do in their domain
  • Build simple prompts that work well on their surface
  • Create deterministic workflows, agents, or skills

This distributes AI capability development across teams, removing the AI team as a bottleneck.

Current State & Challenges

Where It Stands (January 2026)

The prototype validated the approach, but hasn't shipped yet.

Current status:

  • Building with a front-end engineer
  • No set timeline
  • Many competing priorities
  • Still functioning as proof-of-concept and development sandbox

Technical Challenges (Work in Progress)

1. Modal Interactions

The agent struggles when executing multiple actions within modals. When it reads page context again after opening a modal, it gets confused about state.

Current approach:

  • Adjusting the architecture to help context persist better across modal interactions
  • Refining how the agent tracks its position in multi-step workflows

2. Navigation Map Coverage

The agent can only navigate to areas covered in the navigation map I built. Expanding coverage requires manually mapping more of Personio's information architecture.

3. Workflow Completion

Currently, agentic workflows stop short of full completion (e.g., "Request time off" doesn't submit the form). This is intentional — I want users to review before submission — but it means the agent can't fully automate end-to-end processes yet.

What I Learned

Complexity is often artificial. I spent months trying to understand and work within our existing architecture. Two afternoons building from scratch proved that the problem wasn't intrinsically hard — it was that our system had accumulated unnecessary complexity. Sometimes the right move is to start over.

Page context is the unlock. The single biggest difference between my prototype and production wasn't model quality or tool design — it was giving the AI access to what the user was actually looking at. Context awareness transformed the assistant from guessing to knowing.

Prototypes outperform promises. I could have written strategy documents or created mockups. Instead, I built a working system. That demo in the quarterly planning session — showing real capabilities, not hypothetical ones — changed the conversation entirely. "Ship it" isn't a response you get to a slide deck.

The federated model matters more than the prototype. The context drawer isn't just a UI element — it's a framework for distributing AI development. If other teams can define what the assistant does in their domain, we're not just building a better assistant; we're building a platform for the entire company to become agentic.

I can build systems, not just interfaces. Learning to code didn't just make me faster at UI work. It gave me the ability to architect and implement entire systems. That fundamentally changes my role and the problems I can solve.

Technical Details

Tech Stack:

  • Chrome Extension (Manifest V3)
  • Chrome Sidepanel API
  • Service Worker for background processes
  • Content scripts for DOM manipulation and reading
  • Claude Agent SDK (reference architecture)
  • Custom navigation map (JSON structure defining Personio's IA)

Key Technical Decisions:

  • Text-based context only (no screenshots) for performance and token efficiency
  • Context embedded in system prompt, not user messages
  • Tool-based context refresh after agent actions
  • Navigation map as structured data rather than letting agent discover routes

Development Approach:

  • Initial build: 2 afternoons (Dec 16-17, 2024)
  • Ongoing refinement: Continuing with front-end engineer
  • AI-assisted coding throughout
  • Rapid iteration based on testing

Next Steps

Immediate (WIP):

Future Vision:

The prototype proved the concept. Now the question is: how do we scale it?
